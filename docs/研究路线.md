# Anthropic × Theorem：软件工程与形式化验证研究路线

本目录用于阅读与复查 Anthropic 和 Theorem 的合作成果。报告是 **2026 年 10 月 22 日**发布的 [LLMs are making formal software verification feasible at a much larger scale](https://www.anthropic.com/research/formal-verification)。研究主线是把已有 fuzz 入口编译成 RISC-V 程序，将目标性质写成形式化命题，由语言模型生成证明，再交给 Rocq 检查。

三个仓库构成研究公开 OSS Verify 成果的主要入口。**部署仓库、重放公开证明、重新构建被证明的二进制、重新运行 AI 证明生成实验，是四个不同的完成标准。** 本文是学习与复现实验的路线，不是“整篇报告已经复现”的验收报告。

## 把程序 P、规格 S、证明 π 对应到文件

以 `oss-verify-proofs/projects/<project>/<harness>/` 为单位，而不是把整座库作为一个已证明对象。

| 层次 | 文件或制品 | 要回答的问题 |
|---|---|---|
| 源程序与测试入口 | `source/`、上游源码、构建 recipe、`proofs/provenance/` | harness 调用了什么？有断言吗？库和 driver 有哪些改动？ |
| 实际程序 P | 发布的 `plain`、`asan`、`ubsan`、`asan-ubsan` ELF，以及 `Images.v` | 证明究竟绑定哪份机器码？SHA-256 与读取的 ELF 是否一致？ |
| 规格 S | `Statements.v`、`Characterise.v`、`harness.yaml` | 输入、内存、系统调用拒绝和返回状态的前提是什么？ |
| 证明 π | `proofs/<statement>/Proof.v`、`proofs/lib/` | 顶层命题如何依赖函数契约、循环不变量和公共引理？ |
| 检查与可信边界 | `oft check` 生成的 wrapper、`assumptions.out`、允许公理表、LPS | 检查器是否强制定理类型正确？实际依赖了哪些公理？ |

公开证明有些是从早期任务的证明适配而来，不能把源码目录名相同视为二进制及模型始终相同。应沿 provenance、statement fingerprint 和发布清单追踪绑定关系。[证明来源](https://github.com/theorem-labs/oss-verify-proofs/blob/32c8baf6e92f173b445903857770da103ba307e0/docs/origin.md)

检查器先验证二进制 SHA，构建机器映像和声明，再检查证明，并生成具有指定类型的 wrapper、审计其公理。官方镜像提供 Rocq 与依赖，不包含证明生成自动化。可选 `rocqchk` 是另一道检查，不能将常规检查成功写成已经执行了它。[固定检查流程](https://github.com/theorem-labs/oss-verify-proofs/blob/32c8baf6e92f173b445903857770da103ba307e0/docs/checking.md)

## 两个适合精读的入口

**先读 zlib/checksum_fuzzer。** 该基线已有 `plain_halts`、`plain_halts_may_fail` 两项证明；ASan/UBSan 一致性命题仍为 open。harness 有 CRC、Adler 校验相关断言，适合追踪“源代码断言—机器码—允许退出状态—形式化保证”的链条。练习：逐条标记其六项检查，解释哪些断言表达实质规律、哪些依赖前面已断言的相等关系。[入口说明](https://github.com/theorem-labs/oss-verify-proofs/blob/32c8baf6e92f173b445903857770da103ba307e0/projects/zlib/checksum_fuzzer/README.md)

**再读 cjson/cjson_read_fuzzer。** 该基线已有三项 sanitizer agreement 证明，而 halts 命题仍 open。harness 调用解析、打印和压缩函数，但没有检查输出语义正确性的断言。练习：解释为何这些证明不能推出“JSON 解析结果总是符合规范”，也不能从 agreement 自动推出终止。[入口说明](https://github.com/theorem-labs/oss-verify-proofs/blob/32c8baf6e92f173b445903857770da103ba307e0/projects/cjson/cjson_read_fuzzer/README.md)

然后从 LPS 的小型示例或 `oss-verify-proofs/tests/` 入手写自己的证明，先理解状态转换和失败控制，再读大型自动生成文件。[公开证明编写入口](https://github.com/theorem-labs/oss-verify-proofs/blob/32c8baf6e92f173b445903857770da103ba307e0/docs/proving.md)

## 分阶段研究与验收

| 阶段 | 工作 | 可交付证据 |
|---|---|---|
| 1. 读清主张 | 阅读报告、固定版本 README、LPS SCOPE；区分安全性、终止性、一致性、功能正确性 | 一页主张表，每条写清对象、前提与未覆盖范围 |
| 2. 复查已发表证明 | 从上述两个入口起步，在匹配的检查环境中重放 | 每个命题的真实结果、wrapper、公理审计和日志；分别记录冷启动与缓存运行 |
| 3. 解释证明结构 | 从一个顶层命题追到 driver、函数契约、循环引理与指令规则 | 自己绘制的依赖图，以及每个关键引理为何足够的解释 |
| 4. 复建程序制品 | 按该入口的来源记录取源码、recipe、补丁和 builder，重建 ELF | 与发布二进制的 SHA 比较；不匹配时保留差异，不沿用旧证明宣称覆盖新 ELF |
| 5. 做受控修改 | 在实验副本中修改一个小测试或补充断言，观察规格与证明的变化 | 修改前后对照、原证明失效原因、新证明或明确的未完成状态 |
| 6. 尝试 AI 生成 | 选择 toy 或范围明确的小命题，自行设定 agent、模型、预算和停止规则 | 完整提示、工具调用、生成代码、失败尝试、费用/时间及独立检查结果 |
| 7. 扩展公开子集 | 明确资源预算后逐批增加入口 | 固定快照的覆盖矩阵；区分已通过、未运行、环境失败与证明失败 |

第 6 阶段是新的可记录实验，不能仅因用了 Claude 就称为重现了作者的原始生成过程。公开来源说明了任务、提交与验收接口；本目录未取得并核验能逐步重演原研究的完整模型配置、编排与运行轨迹。[任务与证明来源](https://github.com/theorem-labs/oss-verify-proofs/blob/32c8baf6e92f173b445903857770da103ba307e0/docs/origin.md)

## 三个仓库之外还需要什么

**重放证明**需要发布二进制及固定 checker；它们不是把三个 Git 目录复制下来就自然齐备的文件。**重建 ELF**还需要相应源码归档、recipe 或历史 port、补丁、builder 镜像与 sysroot。部分构建会执行刚编译的 RISC-V 工具，另需相应执行支持；每项以锁定的来源记录为准。[复建说明](https://github.com/theorem-labs/oss-verify-proofs/blob/32c8baf6e92f173b445903857770da103ba307e0/docs/reproducing.md)

截图第四个 [static-asan](https://github.com/theorem-labs/static-asan) 不是无关项目：它提供静态 musl/ASan 工具链所需改动。只检查已发布证明时，可使用已固定的检查器与 ELF；研究编译链、sanitizer 的保证或从源代码复建时，应一并阅读它及 `docs/building.md`。这不要求把它当成用户指定的第四个主项目放入目录。[二进制构建与 sanitizer 说明](https://github.com/theorem-labs/oss-verify-proofs/blob/32c8baf6e92f173b445903857770da103ba307e0/docs/building.md)

报告还讨论了 x86 上的 zlib 规格验证、Verus 上的 Python 解释器等案例。这三个仓库主要对应 OSS-Fuzz/RISC-V 这条研究线，不能据此宣称已覆盖整篇报告的全部实验。[报告的其他案例](https://www.anthropic.com/research/formal-verification)

运行入口、环境检查和本次实际验收结果由同目录的部署说明提供；本文不预先将任何尚未执行的阶段标为完成。
